# 第 01 讲 · 从"预测更准"到"决策更优"

## ① 基本信息

| 项 | 内容 |

| 学时 | 4（理论 1.5 / 实践 2.5） |
| 地点 | 机房（分组围坐） |
| 授课人 | 学校教师（3h）+ 企业导师（1h 导入） |
| 方法 | 案例导入、提问链、团队建设、看板演示 |
| 教具 | PPT 01、任务书 T01、便利贴、白板 |

## ② 学习情境

> 周一早上，雅迪某基地设备科长老周找到 IT："3 号线那台主传动电机最近声音不对，
> 你们那个 AI 能不能提前告诉我要不要停机？别到时候停线了才说。"
>
> 上一套系统给过他一份 27 页的诊断报告，结论是"建议关注"。
> 老周的原话是："我要的不是报告，是哪天停、停多久、要几个人、备件有没有。"

这段场景包含三个真实矛盾：**预测 vs 决策、准确 vs 可执行、技术语言 vs 生产语言**。

## ③ 学习目标

- **知识**：能说出预测性维护价值链的四个环节；能复述 ISO 13374 六功能块；能解释 Agent = Model + Harness。
- **技能**：能画出本项目"六功能块 → 系统模块"对应图；能完成团队分工与 Git 仓库初始化。
- **素养**：建立"交付视角"——判断工作好坏的标准是"客户能不能用"，不是"技术先不先进"。

## ④ 重点难点

| 类型 | 内容 | 突破策略 |
|---|---|---|
| 重点 | ISO 13374 六功能块与项目模块的映射 | 用一张"从传感器到工单"的实物链路图，让学生把六块贴到链路上 |
| 重点 | 智能体四要素与 Harness 的存在意义 | 先演示"只有 Prompt 的 Agent"如何失控，再引出约束 |
| 难点 | 从"技术视角"转向"交付视角" | 用老周的三句话做"翻译练习"：技术说法 → 生产说法 |
| 难点 | 学生不理解"为什么要这么多文档" | 展示一次真实返工：需求没写清导致重做 2 周 |

## ⑥ 问题链

1. **"预测准确率 95% 的系统，为什么班组不用？"**
   → 预期：因为没告诉他哪天停、停多久、要谁签字。追问：那准确率重要吗？重要，但不是第一位。
2. **"如果模型说'建议关注'，班组能执行吗？"**
   → 不能。"建议关注"不是动作。动作必须是"某日某时，某人，做某事"。
3. **"六功能块里，哪一块最容易做、哪一块最容易被忽略？"**
   → 最容易 DA（采数据），最容易被忽略 AG（执行与反馈）。
4. **"Agent 和聊天机器人差在哪？"**
   → 差在能不能**动**（调工具）、**记**（记忆）、**被管**（权限/熔断）。
5. **"这门课结束时，你要交出什么？"**
   → 一个能被别人验收的系统，不是一份报告。

3. ISO 13374：DA/DM/SD/HA/PA/AG，逐块举例（PPT 7–8）
4. Agent 四要素与 Harness 七组件（PPT 9–10）
5. 课程地图：4 模块 16 讲 16 工件（PPT 11）
6. 交付标准预览：42 项验收清单长什么样（PPT 12）
7. 团队与角色：6 岗位职责（PPT 13）

## ⑧ 实操任务（T01）

1. 4–5 人组队，确定组名与口号（5′）
2. 认领 6 个角色：项目经理 / 算法数据 / 后端 / 前端可视化 / 测试 / 安全交付（10′）
3. 建 Git 仓库 `pdm-team-{N}`，按规范建目录（`artifacts/`、`docs/`、`src/`、`tests/`）（15′）
4. 写 `README.md`：组名、成员、角色、协作规约（分支策略、提交信息格式、评审规则）（15′）
5. 建看板：16 个工件任务卡，标注负责人与截止周（15′）
6. 提交首个 commit，截图存档（5′）

**卡点提示**：Git 用户名为空、换行符警告、看板字段缺失——助教提前准备检查脚本。

# 第 02 讲 · 需求工程：把一句抱怨变成可验收的规格

## ① 基本信息

| 项 | 内容 |
|---|---|
| 学时 | 4（理论 1.0 / 实践 3.0） |
| 授课人 | 学校教师（2h）+ 企业导师（2h 评审） |
| 方法 | 反例教学、EARS 转写、评审会模拟 |
| 教具 | PPT 02、任务书 T02、反例需求书（打印）、评审记录表 |

## ② 学习情境

> 老周又来了，这次带了三句话：
> ①"要能提前一周知道设备快坏了"；
> ②"别老报警，一天几十条谁受得了"；
> ③"真要大修，得让我提前备件、提前排产"。
>
> 项目经理把这三句话写成需求："系统应具备高准确性预测能力，报警要及时准确，支持维修决策。"
> 评审会上，老周问了一句："**准确率多少算准确？提前一周是 7 天还是 5 天？**" 全场沉默。

## ③ 学习目标

- **知识**：说出 EARS 五种句式；说出 FR 与 NFR 的区别；说出验收标准三要素。
- **技能**：把 3 条口语需求转写为 ≥10 条 FR + ≥5 条 NFR；建立 RTM 追溯矩阵。
- **素养**：形成"不可判定的需求 = 无效需求"的职业习惯。

## ④ 重点难点

| 类型 | 内容 | 突破策略 |
|---|---|---|
| 重点 | 验收标准的可判定性 | 用"能否写出一条测试用例"作为判定标准，现场逐条试写 |
| 重点 | NFR 的量化 | 给 NFR 模板：指标 + 阈值 + 测量方法 + 测量条件 |
| 难点 | 区分"需求"与"方案" | 反例："用 Kafka 做消息队列"是方案不是需求；改为"事件端到端延迟 ≤ 2s" |
| 难点 | 学生爱写"系统应友好/高效/稳定" | 现场"删词游戏"：删掉所有形容词，看还剩什么 |

## ⑤ 行动六步时间轴

| 时间 | 阶段 | 教师活动 | 学生活动 | 媒体 |
|---|---|---|---|---|
| 0–10 | 情境唤醒 | 读反例需求书，请学生扮演老周提问 | 找茬：哪句无法验收 | PPT 4 |
| 10–15 | 目标对齐 | 亮目标与验收标准（本讲产出 15 条需求） | 记录 | PPT 3 |
| 15–50 | 知识建构 | EARS 五句式；FR/NFR；验收标准三要素；RTM；变更控制 | 跟写 3 条示例 | PPT 6–10 |
| 50–60 | 休息 | — | — | — |
| 60–70 | 任务下达 | 发 T02；给出三句话原文与业务背景卡 | 拆解：谁、什么时候、要什么 | 任务书 |
| 70–80 | 方案决策 | 各组说"我们打算拆成几条需求" | 互评：有没有漏掉"报警疲劳" | 白板 |
| 80–130 | 实操实施 | 巡场；重点看 NFR 是否量化 | 写 10 FR + 5 NFR + RTM | 模板 |
| 130–155 | 企业评审 | 企业导师逐组点评（每组 3 分钟） | 记录修改意见 | 评审表 |
| 155–170 | 检查验收 | 按 DoD 抽检 2 组 | 交叉验收 | 验收单 |
| 170–180 | 复盘评价 | 复盘三问；总结"三句最常见的废话需求" | 记录 | PPT 16 |

## ⑥ 问题链

1. **"'及时准确'——及时是几秒？准确是几个百分点？"**
   → 逼出量化。报警延迟 ≤ 30s；误报率 ≤ 5%/周/设备。
2. **"这条是需求还是方案？"**（出示"用 Kafka"）
   → 方案。需求应写"事件端到端延迟 ≤ 2s，峰值 5000 条/秒"。
3. **"如果只能留 5 条需求，留哪 5 条？"**
   → 训练 MoSCoW 优先级，逼学生想"什么才是核心价值"。
4. **"需求改了，怎么知道哪些测试要改？"**
   → RTM：需求 ID → 设计 → 用例，一处改三处查。
5. **"验收时甲方说'不是这个意思'，谁的责任？"**
   → 需求评审签字缺失的责任；引出评审记录与基线冻结。

## ⑦ 讲授提纲

1. 反例拆解：一份无法验收的需求书（PPT 4–5）
2. EARS 五句式与中文写法（PPT 6）
3. FR/NFR 编号与优先级（PPT 7）
4. 验收标准三要素 + 正反例（PPT 8）
5. RTM 追溯矩阵（PPT 9）
6. 需求变更控制与基线（PPT 10）

## ⑧ 实操任务（T02）

1. 读业务背景卡（设备类型、传感器、班组结构、现有系统）（5′）
2. 用 EARS 写 10 条 FR，每条含 ID、描述、优先级、验收标准（35′）
3. 写 5 条 NFR：性能、可靠性、安全、可维护、合规（20′）
4. 建 RTM：需求 → 模块 → 测试用例（占位）（15′）
5. 标注 3 条"待确认问题"（给企业导师）（5′）
6. 评审后修订，输出 v0.2 + 变更说明（10′）

**卡点提示**：学生容易把"预测"写成一条巨型需求——提示按"数据→诊断→预测→决策→通知"拆。

## ⑨ 检查表（DoD）

- [ ] 每条 FR 有唯一 ID、可判定的验收标准
- [ ] 5 条 NFR 全部量化（含测量方法）
- [ ] RTM 无孤立需求、无孤立用例
- [ ] 至少 3 条待确认问题已列给企业方
- [ ] 无"友好/高效/稳定/智能"等不可判定形容词

## ⑩ 评价（本讲 3 分）

| 评分点 | 权重 | 评分人 |
|---|---|---|
| 需求可判定性 | 40% | 教师 |
| NFR 量化质量 | 25% | 教师 |
| RTM 完整性 | 20% | 助教 |
| 评审应对（能否答"凭什么"） | 15% | 企业导师 |

## ⑪ 差异化

- **快班**：增加"需求冲突"练习（预测要准 vs 报警要少）。
- **慢班**：给 10 条需求的"骨架"，只填验收标准。

## ⑫ 作业与反思

- 作业：按评审意见修订为 v1.0，写 200 字变更说明。
- 反思：企业导师点评中反复出现的词，记录下来作为下轮教学重点。

# 第 03 讲 · 架构与领域：六功能块到限界上下文

## ① 基本信息

| 项 | 内容 |
|---|---|
| 学时 | 4（理论 1.5 / 实践 2.5） |
| 方法 | 事件风暴、C4 建模、架构走查 |
| 教具 | PPT 03、任务书 T03、便利贴（4 色）、大白纸、Mermaid 模板 |

## ② 学习情境

> 第 2 周，团队把需求交给外包做了一版"万能服务"：一个 Python 文件 3000 行，
> 查设备、算指标、发告警、建工单、调备件全在里面。
> 第 3 周加"多基地"需求，改一处崩三处。外包说："你们的需求老变。"
> 团队说："你们的架构扛不住变。"

## ③ 学习目标

- **知识**：说出 C4 四层视图；说出限界上下文的判定依据；区分命令、事件、策略。
- **技能**：完成一次事件风暴；画出 Context/Container 图；输出 ≥12 条领域事件。
- **素养**：建立"边界意识"——先想清楚"谁不负责什么"。

## ④ 重点难点

| 类型 | 内容 | 突破策略 |
|---|---|---|
| 重点 | 按业务能力划分上下文 | 用"如果这个模块独立成公司，它卖什么"来检验边界 |
| 重点 | 领域事件命名（过去式） | 事件必须能回答"已经发生了什么"，不能是"请做某事" |
| 难点 | 同步与异步的取舍 | 给判定表：是否要求强一致 / 是否跨组织 / 能否容忍延迟 |
| 难点 | 学生画图变成"技术堆栈图" | 禁止在 Container 图里出现框架名，只写职责与协议 |

## ⑤ 行动六步时间轴

## ⑥ 问题链

1. **"设备档案和诊断，为什么不能放一个上下文？"**
   → 变更频率不同、一致性要求不同、团队可并行。
2. **"告警是事件还是命令？"**
   → 事实是事件（AlertRaised），"请处理"是命令（AckAlert）。
3. **"诊断完成到生成工单，必须同步吗？"**
   → 不必。可异步，容忍秒级延迟，换取解耦。
4. **"边缘断网时，哪个上下文必须活？"**
   → 采集、诊断、本地告警；决策可降级。
5. **"如果一个上下文只有一张表，它还有存在意义吗？"**
   → 有，如果它有独立的业务规则与变更节奏。

## ⑦ 讲授提纲

1. 反例：万能服务的三次崩溃（PPT 4–5）
2. C4：Context / Container / Component / Code（PPT 6）
3. 事件风暴：命令、事件、聚合、策略、读模型（PPT 7）
4. 本项目 8 个上下文与职责边界（PPT 8）
5. 同步 vs 异步判定表（PPT 9）

# 第 04 讲 · 数据与特征：1 亿行到 5 维 HI

## ① 基本信息

| 项 | 内容 |
|---|---|
| 学时 | 4（理论 1.5 / 实践 2.5） |
| 方法 | 公式推导、代码走读、对照实验 |
| 教具 | PPT 04、任务书 T04、样本数据集（3 组完整度）、Jupyter/脚本模板 |

## ② 学习情境

> 现场只装了振动和温度传感器，没有电流互感器。
> 系统算出 HI=82，判定"绿色，正常"。
> 老周问："你就凭两个数说我设备正常？"
> 工程师答："模型就是这么算的。"
> 老周："那你这模型，我不敢用。"

**核心问题**：缺数据时，系统该说"正常"还是"我不知道"？

## ③ 学习目标

- **知识**：说出五维指标（振动/峭度/温升/电流偏差/劣化速率）的物理含义与归一化方法；说出单维致命短路与缺维重归一规则。
- **技能**：用真实指标计算 HI；构造缺失维度场景并正确标记降级；解释每个维度的贡献。
- **素养**：建立"数据不足就说数据不足"的诚实原则（项目宪法第四条）。

## ④ 重点难点

| 类型 | 内容 | 突破策略 |
|---|---|---|
| 重点 | 归一化的物理意义（为什么是 /3、/4、/15、/25、/5） | 每个分母对应一个"致命值"，让学生反推工程含义 |
| 重点 | 单维致命短路（s≥1 → HI=0） | 用"温度爆表但振动正常"的案例说明为什么不能平均 |
| 难点 | 缺维重归一导致"看起来正常" | 实验对比：完整 5 维 vs 缺 2 维，HI 相同但置信度不同 |
| 难点 | 基线与阈值的适用场景 | 有历史基线用基线，无基线用 ISO 20816 分区 |

## ⑥ 问题链

1. **"振动 RMS 从 2.8 涨到 4.5，算坏吗？"**
   → 看基线/分区，不只看绝对值。基线 2.0 时 span_ratio=3，s=(4.5-2)/(2*3)=0.42。
2. **"温度 95℃、振动正常，HI 该是多少？"**
   → 温升超 15℃ → s≥1 → 短路 HI=0，不是加权平均。
3. **"缺了电流维度，HI 还是 82，能说设备健康吗？"**
   → 不能。必须 `degraded=true`，并下调置信度、缩短复检周期。
4. **"权重 0.35 给振动，凭什么？"**
   → 振动对旋转机械故障最敏感；权重可配置，但必须有依据。
5. **"HI=60 和 HI=59 有本质区别吗？"**
   → 分级是管理工具，不是物理突变；要说明"临界区需人工复核"。
