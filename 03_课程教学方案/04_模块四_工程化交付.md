## ② 学习情境

> 上线前，API 测试 66 项全绿，单元测试 146 项全绿。
> 上线当天，管理台白屏。查了 3 小时，发现是一个按钮的 `onclick` 绑到了不存在的函数名。
>
> 后端工程师说："我接口是好的。"
> 前端工程师说："我本地是好的。"
> 测试工程师说："我测了接口。"
>
> **三层都"对"，系统是坏的。**

## ③ 学习目标

- **知识**：说出测试金字塔四层与本项目配比；说出 Mock 的适用边界；说出缺陷报告六要素。

## ④ 重点难点

| 类型 | 内容 | 突破策略 |

| 重点 | 测试分层与职责边界 | 用"三层都绿但系统坏"的案例说明层间空隙 |
| 重点 | 缺陷报告可复现 | 要求"换一个人按报告能复现"作为验收标准 |
| 难点 | Mock 掩盖真实问题 | 展示 mock 通过但真实 DB 报 500（表名错）的案例 |
| 难点 | 浏览器层价值 | 现场演示 API 正常但页面白屏 |

## ⑥ 问题链

1. **"单测全绿，为什么系统还是坏的？"**
   → 单测只测函数；集成、契约、UI 都没覆盖。
2. **"Mock 什么时候会骗你？"**
   → 当 Mock 的假设与真实环境不一致（表名、字段类型、时区）。
3. **"为什么要有浏览器层测试？"**
   → 它测的是"用户能不能用"，不是"接口通不通"。
4. **"缺陷报告写给谁看？"**
   → 写给"没参与开发的人"，他必须能复现。
5. **"测试通过率 100% 能说明什么？"**
   → 只能说明"已测的部分没问题"，不能说明"没测的部分没问题"。

# 第 14 讲 · 云边部署：K3s + SQLite 双后端（企业导师主讲 2h）

## ① 基本信息

| 项 | 内容 |
|---|---|
| 学时 | 4（理论 1.5 / 实践 2.5） |
| 地点 | 机房 + 企业现场/远程 |
| 授课人 | 企业导师（2h 部署实操）+ 学校教师（2h） |
| 方法 | 架构讲解、部署实操、断网演练 |
| 教具 | PPT 14、任务书 T14、K3s 单节点/模拟环境、部署脚本、站点注册表 |

## ② 学习情境

> 印尼基地：一条产线，两台服务器，网络每周断 3 次，现场没有 DBA。
> 集团方案要求"数据不出厂"，但又要"总部能看到各基地健康度"。
>
> 架构师给了两个选项：
> A. 每个基地装一套 TiDB（3 节点起步，运维成本高）；
> B. 边缘用 SQLite 单文件，只上行摘要。
>
> 选 B。理由不是"SQLite 更先进"，而是"**在 2C4G 和无人值守的条件下，B 能活**"。

## ③ 学习目标

- **知识**：说出边缘选型的四个约束；说出 SQLite WAL 的适用与边界；说出五类 SQL 方言差异；说出联邦的三张表。
- **技能**：完成边缘站点部署与注册；验证双后端行为一致；执行断网降级与恢复补传。
- **素养**：建立"约束驱动选型"意识——没有最好的技术，只有最合适的约束解。

## ④ 重点难点

| 类型 | 内容 | 突破策略 |
|---|---|---|
| 重点 | 双后端抽象与方言翻译 | 现场改一条 SQL，看两种后端结果是否一致 |
| 重点 | 站点注册与摘要上行 | 画时序：注册 → 心跳 → 摘要 → 汇总 |
| 难点 | 数据主权与联邦一致性 | 用"哪些数据能出厂"分级表讨论 |
| 难点 | 断网时的行为 | 断网演练：本地可用、标记降级、恢复补传 |

## ⑤ 行动六步时间轴

| 时间 | 阶段 | 教师活动 | 学生活动 | 媒体 |
|---|---|---|---|---|
| 0–10 | 情境唤醒 | 讲印尼基地的四个约束 | 讨论：选 A 还是 B | PPT 4 |
| 10–15 | 目标对齐 | 亮目标；说明部署单验收标准 | 记录 | PPT 3 |
| 15–40 | 知识建构 | 边缘约束；SQLite WAL；五类方言；联邦三表；数据分级 | 跟读一段方言翻译 | PPT 6–9 |

| 100–140 | 实操实施 | 巡场；检查是否验证了一致性 | 部署、注册、上行、断网 | 终端 |

## ⑥ 问题链

1. **"为什么边缘不用 TiDB？"**
   → 资源、运维、成本、断网四约束；不是能力问题，是适配问题。
2. **"SQLite 能撑多少并发？"**
   → 单写多读，WAL 下读不阻塞写；写并发高会锁等待，需限流。
3. **"为什么要有方言翻译层？"**
   → 同一套业务代码跑两种库，避免维护两套 SQL。
4. **"哪些数据能出厂？"**
   → 摘要、指标、告警；原始波形与工艺参数不出厂。
5. **"断网 3 天，恢复后会发生什么？"**
   → 本地继续跑；恢复后补传摘要，按时间戳去重。

## ⑦ 讲授提纲

1. 印尼基地的四个约束（PPT 4–5）
2. 边缘架构：K3s + SQLite + 摘要上行（PPT 6）
3. SQLite WAL 与并发边界（PPT 7）
4. 五类方言翻译（占位符/upsert/ignore/时间函数/间隔）（PPT 8）
5. 联邦三表与判据下发（PPT 9）
6. 数据主权分级与断网策略（PPT 10）

## ⑧ 实操任务（T14）

1. 读部署清单，确认资源与端口（10′）
2. 部署边缘服务（容器/进程），验证健康检查（20′）
3. 注册站点，写入 `site_registry`（10′）
4. 上行一条摘要，验证 `read_edge_summary`（10′）
5. 跑同一组 SQL 在两种后端，比对结果（15′）
6. 断网 5 分钟，验证本地可用 + 降级标记（10′）
7. 恢复网络，验证补传与去重（10′）

**卡点提示**：SQLite 用内存模式导致重启丢数据；`isolation_level` 未设 None 导致事务不提交。

## ⑨ 检查表（DoD）

- [ ] 边缘服务健康检查通过，数据落盘可重启恢复
- [ ] 站点注册成功，摘要可查
- [ ] 同一 SQL 在两种后端结果一致（至少 5 条）
- [ ] 断网时本地诊断可用且 `degraded=true`
- [ ] 恢复后摘要成功补传且无重复

| 评分点 | 权重 | 评分人 |
|---|---|---|
| 部署正确性 | 30% | 企业导师 |
| 双后端一致性 | 25% | 教师 |
| 断网演练表现 | 25% | 企业导师 |
| 部署单/回滚方案 | 20% | 教师 |

## ⑪ 差异化

- **快班**：增加"判据下发版本不一致"的排查。
- **慢班**：提供一键部署脚本，重点在验证与记录。

## ⑫ 作业与反思

- 作业：写一页《海外基地数据合规建议》。
- 反思：企业导师的"现场约束"要讲够，否则学生会觉得 SQLite 是"降级方案"。

# 第 15 讲 · 可观测与治理：OTel/漂移/A2A

## ① 基本信息

| 项 | 内容 |
|---|---|
| 学时 | 4（理论 1.0 / 实践 3.0） |

## ② 学习情境

> 客户投诉："昨天诊断结果不对。"
> 团队查了 6 小时：日志有，但没有 trace_id 串起来；
> 模型版本换了，但没人知道是哪天换的；
> 供应商那边说"我们按你们接口调的"，但没有任何调用记录。
>
> 三件事，三个缺失：**可观测、可追溯、可协作**。

## ③ 学习目标

- **知识**：说出 GenAI span 三层结构；说出模型版本登记字段；说出双窗口 z 漂移检测原理；说出 A2A 的 Agent Card 与任务状态。
- **技能**：配置 trace 并下钻到工具级；登记模型版本；跑一次漂移检测；完成一次 A2A 调用。
- **素养**：建立"没有记录就等于没发生"的工程习惯。

## ④ 重点难点

| 类型 | 内容 | 突破策略 |
|---|---|---|
| 重点 | trace 的父子关系 | 画一张"请求→循环→工具→DB"的 span 树 |
| 重点 | 版本可追溯 | 每个预测结果必须能回答"哪个模型版本算的" |
| 难点 | 漂移阈值与误报 | 用两组数据对比：真漂移 vs 季节波动 |
| 难点 | 跨组织调用的信任边界 | 讨论：供应商能看什么、不能看什么 |

## ⑥ 问题链

1. **"日志和 trace 有什么区别？"**
   → 日志是点，trace 是线；没有线，点再多也串不起来。
2. **"模型版本为什么要登记？"**
   → 出了问题要能回答"哪个版本、什么时候、谁批的"。
3. **"漂移检测为什么用双窗口？"**
   → 短窗口灵敏、长窗口稳；两者对比降低误报。
4. **"z 值多大算漂移？"**
   → 经验阈值（如 |z|>2），需结合业务误报率调。
5. **"供应商能调我们的工具吗？"**
   → 通过 A2A 暴露受限任务，不给内部工具直连；Agent Card 声明能力边界。

| 教具 | PPT 16、42 项验收清单、计时器、评分表、交付包模板 |

## ② 学习情境

> 周五下午，客户发来一句话："下周一验收，请准备好材料。"
> 团队翻遍仓库：代码有、文档有、测试有，但**没人能证明"这些加起来是一个能用的系统"**。
>
> 交付不是"我做完了"，是"**我能证明我做完了，且别人验收通过**"。

## ③ 学习目标

- **知识**：说出验收清单六大类；说出答辩五段结构；说出复盘四问。
- **技能**：完成 42 项自检并给出证据；8 分钟讲清"问题—方案—证据—价值"；写出可复用经验。
- **素养**：建立"交付即承诺"的职业态度与复盘习惯。

## ④ 重点难点

| 类型 | 内容 | 突破策略 |
|---|---|---|
| 重点 | 证据组织 | 每个清单项必须有"证据位置"（文件/命令/截图） |
| 重点 | 答辩结构 | 给模板 + 计时演练（超时扣分） |
| 难点 | 把技术讲成价值 | 用"省了多少停机小时/多少钱"换算 |
| 难点 | 承认不足 | 复盘要求写 3 条"没做好"，不许写"时间不够" |

## ⑥ 问题链

1. **"清单上打勾了，证据在哪？"**
   → 每一项必须能指到文件、命令或截图。
2. **"你的系统解决了什么问题，值多少钱？"**
   → 用停机小时 × 每小时损失 + 减少的误报工时换算。
3. **"如果现在让你上线，你敢吗？为什么？"**
   → 敢/不敢都要给理由（降级、回滚、监控）。
4. **"这次最该改的一件事是什么？"**
   → 必须是具体动作，不能是"多留时间"。
5. **"你学到的最有用的一件事，能教给别人吗？"**
   → 检验是否真的理解（费曼技巧）。

## ⑦ 讲授提纲

1. 交付不是做完，是能证明（PPT 4–5）
2. 42 项清单六大类（PPT 6）
3. 答辩五段结构（PPT 7）
4. 评委常问 10 题与回答要点（PPT 8）
5. 复盘四问与经验卡（PPT 9）

## ⑧ 实操任务（T16）

1. 逐项自检 42 项，填证据位置（20′）
2. 补 3 个最弱的证据（20′）
3. 写答辩 PPT（8 页以内）（30′）
4. 组内计时演练 1 遍（15′）
5. 正式答辩（8′ + 7′）（40′）
6. 写复盘报告：四问 + 3 条经验 + 3 条改进（20′）

**卡点提示**：PPT 超过 8 页、前 3 分钟讲背景、问答环节答非所问。

## ⑨ 检查表（DoD）

- [ ] 42 项清单通过率 ≥ 70%
- [ ] 每项有证据位置
- [ ] 答辩 PPT ≤ 8 页，8 分钟内讲完
- [ ] 能回答"证据在哪""值多少钱""敢不敢上线"
- [ ] 复盘报告含 3 条可复用经验
